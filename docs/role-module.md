# Role Module

## Реализованные сценарии

Зависимости явно собираются в cmd/service/main.go: pool → Transactor →
репозитории агрегатов → usecase → HTTP handlers → сервер.

В internal/usecase/role находятся Get/Delete, в roletemplate — Get/Page/Delete
и проверка принадлежности системе, в roleassignment — List/Assign/Revoke.
Создание и изменение роли и шаблона выделены в createrole/updaterole и
createtemplate/updatetemplate: эти сценарии используют каталог прав и правила
изменения агрегата. listroles дополнительно проверяет фильтр права по каталогу.
listroleassignments читает проекцию назначения с именем и scope роли через
отдельный Reader. Каждый пакет объявляет интерфейсы потребителя в interface.go.
Каталог прав обслуживает permission.Usecase.

Фильтры принадлежат потребляющим usecase. Общие параметры страниц, сортировка
и результат Page находятся в internal/pagination. Доменные агрегаты не зависят
от фильтров или пагинации. Основания выбора пакетов и схема зависимостей
описаны в [архитектуре](architecture-review.md).

Create/Update принимают Params. Actor ID передаётся отдельным аргументом из
доверенного вызывающего кода. Update полностью заменяет имя и права.
Для Update/Delete обязательна ожидаемая версия. При изменении имени и прав
прикладной сценарий нормализует итоговую версию до expected_version + 1.
Запрос без изменений сохраняет версию и не добавляет событие.

PermissionCatalog проверяет коды и scope, объединяет дубликаты. Роли и шаблоны
не допускают пустых наборов. Каталог возвращает возможные права данного типа
scope, а не эффективные права текущего пользователя.

Шаблон заполняет клиентскую форму. Создание роли использует обычный Create;
Клиент может изменить набор прав перед созданием обычной роли.
Instantiate и сохраняемой связи с шаблоном нет.
Поддержаны все три целевых scope, допускаемые текущим доменом.

## Хранение

Именованные SQL-запросы находятся в internal/repository/{role,roletemplate,roleassignment}/queries.sql.
Bob генерирует отдельные пакеты в internal/generated/bob/{role,roletemplate,roleassignment}.
Цель make generate-sql временно копирует SQL в каталоги генерации и удаляет копии
при завершении. make generate запускает SQL и API генерацию. Для SQL нужна
мигрированная PostgreSQL и PSQL_DSN (по умолчанию DATABASE_URL).
Сгенерированные файлы не редактируются вручную.

Настройки `bobgen.yaml` отображают PostgreSQL INT в Go int,
а массивы строк — в []string для сканирования через pgx.
Версия агрегата остаётся BIGINT/int64.

Goose-миграция создаёт roles, role_permissions, role_assignments,
role_templates, template_permissions и outbox_messages.
Доменные идентификаторы представлены INT в PostgreSQL и int в Go.
ID ролей и шаблонов создаёт PostgreSQL через GENERATED ALWAYS AS IDENTITY.
Конструкторы оставляют ID равным нулю; Insert возвращает новую модель с ID
и временем из RETURNING после успешного завершения транзакции.
Тексты прав остаются в каталоге; в БД записываются только PermissionCode.
Имена ролей не объявлены уникальными: такого бизнес-правила в требованиях нет.
Внешние пользователи и ресурсы scope не дублируются в этой БД.

Репозитории заполняют публичные поля Role и RoleTemplate из строк Bob;
RestoreRoleAssignment восстанавливает закрытое состояние назначения.
При чтении ID и время не генерируются заново. PostgreSQL хранит время с
микросекундной точностью; при чтении оно не подменяется временем загрузки.
Чтение агрегата и прав выполняется одним SQL-запросом с единым снимком.

Границы транзакций:

- создание/изменение роли: строка роли, набор прав, запись outbox;
- удаление роли: строка, каскадные права и назначения, запись outbox;
- назначение/отзыв: назначение и запись outbox, с блокировкой строки роли;
- создание/изменение шаблона: шаблон и полный набор прав;
- удаление шаблона: шаблон и каскадное удаление его прав.

Update использует условие по ожидаемой версии. Delete проверяет версию под
блокировкой строки. Конфликт версии возвращает domain.ErrConflict,
отсутствующий объект — ErrNotFound, в том числе при конкурентном удалении.
Повторное назначение возвращает исходную запись без нового события, автора и времени.
Повторный отзыв возвращает успех без события, если роль ещё существует.
Списки пусты при отсутствии совпадений. Ошибки драйвера, не относящиеся
к этим контрактам, возвращаются вызывающему коду.

Outbox содержит RoleCreated, RoleUpdated, RoleDeleted, RoleAssigned и
RoleRevoked. RoleUpdated хранит полный актуальный набор кодов. Это локальный
формат сохранения событий; контракт внешней доставки, упорядочение, повторные
попытки и обработка в AuthZ ещё не реализованы.

## Подключение и запуск

Сервис и команда миграций используют DATABASE_URL своей БД roles-service.
При отсутствии настройки сервис завершается с ошибкой. Ожидание подключения
при запуске ограничено десятью секундами; пул закрывается при завершении.

Для собственной локальной БД можно использовать compose.yaml:

1. Задать ROLES_DATABASE_PASSWORD своим паролем.
2. Выполнить docker compose up -d roles-db.
3. Задать DATABASE_URL с пользователем roles_service, БД roles_service,
   адресом 127.0.0.1:55432 и выбранным паролем (URL-кодировать спецсимволы).
4. Выполнить go run ./cmd/migrate, затем go run ./cmd/service.

Миграции запускаются отдельно, автоматически при старте сервиса не применяются.
Команда service проверяет подключение, собирает модуль и запускает HTTP-сервер.
Адрес задаётся через HTTP_ADDR, по умолчанию :8080. Таймаут заголовков — 5 секунд,
чтения — 15, записи — 30, простаивающего соединения — 60 секунд.
При SIGINT/SIGTERM сервер завершает обработку запросов (до 10 секунд),
затем закрывается пул PostgreSQL.

Технический пример service-tracker изучен в revision
1b9a0022cb6734a86b76be0ddffc268b8263515d: pgxpool, Goose, отдельная команда
миграций и интерфейсы потребителя. Его БД и секреты не используются.
Границы транзакций принадлежат usecase. postgres.Transactor.InTx передаёт
транзакцию через context; postgres.Executor выбирает её вместо пула. Вложенный
InTx использует ту же транзакцию; ошибка должна дойти до внешнего вызова для отката.
Страницы используют InReadTx: read-only repeatable-read сохраняет единый снимок
для count и данных. Репозитории самостоятельно транзакций не открывают.
Общий postgres.MapError сохраняет ErrNotFound/ErrConflict и исходные неизвестные ошибки.

## Неподключённые интеграции

По уточнению задачи AuthZ сейчас не подключается. Прикладной модуль не
проверяет полномочия и предназначен для доверенного вызывающего кода.
Разрешающей заглушки нет. До публикации HTTP API необходимо добавить
обязательные проверки через контракт AuthZ перед чтением/изменением данных,
определить фильтрацию списков и правила просмотра каталога.
Для system-scope шаблонов текущий каталог не содержит специальных прав
управления; это открытый вопрос для этапа AuthZ.

HTTP-адаптер должен установить actor ID из аутентифицированного контекста.
Контракт подключения — `api.Authenticate`: функция проверяет credentials запроса
и возвращает положительный ID пользователя. Непроверенный заголовок не является
источником actorID. В main аутентификатор пока не задан: все запросы отклоняются
с 503. Для интеграции нужно определить проверку JWT или контракт сервиса идентификации.
Ошибочные credentials должны возвращать 401; технические ошибки проверки — 500/503.
Publisher будет читать outbox; AuthZ/SpiceDB handlers будут отдельной
интеграцией. Наличие записей outbox не означает, что права применены в AuthZ.

## HTTP API

OpenAPI и конфигурация генератора: `api/server/roles/`.
Generated-код: `internal/generated/api/server.go`.
Strict handlers и HTTP middleware: `internal/api/`.

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| POST, GET | /roles | Создание, список по scope_type и scope_id |
| GET, PUT, DELETE | /roles/{id} | Получение, изменение, удаление |
| POST, GET | /role-templates | Создание, список по system_id и target_scope_type |
| GET, PUT, DELETE | /role-templates/{id} | Получение, изменение, удаление; обязательный system_id, при несовпадении 404 |
| GET | /roles/{role_id}/assignments | Назначения роли |
| PUT, DELETE | /roles/{role_id}/assignments/{user_id} | Назначение, отзыв |
| GET | /users/{user_id}/role-assignments | Роли пользователя; scope_type и scope_id обязательны |
| GET | /permissions | Каталог по scope_type |

PUT роли/шаблона принимает expected_version в JSON, DELETE — в query-параметре.
PUT полностью заменяет имя и права: оба поля обязательны; пустой набор запрещён.
Имена после TrimSpace содержат 1–200 Unicode-символов. HTTP запрещает повторные коды.
Идентификаторы — положительные целые числа; даты — RFC 3339.
Роли и шаблоны возвращают permissions с code, scope_type, title, description из каталога.
В запросах остаётся permission_codes, а в БД и outbox — только коды.
Ответы об ошибках имеют code, message и при применимости details; детали 500 остаются в логе.
actorID/createdBy/assignedBy не принимаются в теле запроса.

Генерация: `make generate-api`. Без Make:

```sh
go tool oapi-codegen -config api/server/roles/oapi-codegen.yaml api/server/roles/openapi.yaml
go tool golangci-lint run
```

Референс HTTP-слоя — service-tracker, ревизия
`1b9a0022cb6734a86b76be0ddffc268b8263515d`: Echo v5.4.2,
oapi-codegen v2.8.0, echo-v5-middleware v0.2.1, runtime v1.7.0.
Здесь один контракт для связанного модуля, а генерация ID
остаётся в PostgreSQL через Bob. Идентификация в референсе также не подключена.
Проверки полномочий через AuthZ ещё не реализованы; аутентификация и OpenAPI
валидация их не заменяют.

## Клиентские списки и совместимость

Списки ролей, шаблонов и назначений возвращают `{items: [], total, limit, offset}`.
limit по умолчанию 20 (1–100), offset по умолчанию 0. total учитывает фильтры до
пагинации и остаётся корректным на пустой странице. Подсчёт и страница читаются
в одной repeatable-read транзакции. GET /permissions остаётся массивом.

Для ролей и шаблонов search ищет буквальную подстроку имени без учёта регистра.
Символы % и _ обычные. Для ролей permission_code отбирает содержащие право роли.
sort: name, created_at, updated_at; direction: asc, desc. По умолчанию —
created_at DESC, id DESC. ID разрешает совпадения основного ключа сортировки.
Назначения отсортированы по role_id, user_id; пользовательская выборка получает
название и scope роли через JOIN, без запросов к сервису пользователей.

PUT назначения возвращает 201 с RoleAssignment при создании и 200 с прежней записью
при повторе. DELETE возвращает 204 для уже отсутствующего назначения и 404,
если отсутствует сама роль. Удаление роли каскадно удаляет назначения и права;
RoleDeleted сохраняется в той же транзакции. Событие содержит ID роли и scope,
но не список пользователей. Будущему потребителю AuthZ требуется операция удаления
всех отношений по ID роли; контракт такого обработчика пока не определён.

Коды ошибок: invalid_input (поля/фильтры), unknown_permission_code,
permission_scope_mismatch, empty_permissions (400); not_found (404),
version_conflict (409), internal_error (500). unauthorized/unavailable сохраняют
статусы идентификации 401/503. Details содержит field, code, message.

Несовместимые изменения: /templates заменён на /role-templates; ответы объектов
заменили permission_codes на permissions; списки стали страницами; error заменён
на message; PUT назначения теперь возвращает объект и 200/201 вместо 204.
Внешних потребителей или требований сохранения /templates в репозитории не найдено.
Примените миграцию 002_name_limits перед запуском: существующие имена длиннее
200 символов потребуется явно исправить; миграция не обрезает пользовательские данные.

GET /role-assignments возвращает назначения всех пользователей выбранного scope. Параметры scope_type и scope_id обязательны; limit (1–100, по умолчанию 20) и offset задают пагинацию. Ответ содержит items, total, limit, offset; элементы включают user_id, role_id, role_name и scope.
